## 3. Применённые приёмы работы с ИИ

1. **Файл правил** (`CLAUDE.md`) читается агентом автоматически: стек, структура, запреты (`fetch` только через `src/api`, без `dangerouslySetInnerHTML`, не менять бэкенд).
2. **Структура шаблонов RTCF из ДЗ2** (роль, задача, контекст, формат) использовалась как каркас для формулировки задач агенту. Отдельных запусков по шаблонам «по бумажке» не было.
3. **Цепочка шагов**: сначала контракт API и хуки состояния, затем компоненты, затем страницы, затем тесты, затем проверка в браузере, как в Chain-of-Thought из ДЗ2.
4. **Отладка по факту, а не по догадке**: скриншоты и замер DOM через `getBoundingClientRect`, консоль браузера, прямой запрос к API для сверки того, что показывает интерфейс.
5. **Тест, который обязан упасть**: после исправления дефекта временно отключил исправление и убедился, что тест краснеет.
6. **Независимые источники истины**: интерфейс сверялся с ответом сервера (`curl`), а не с самим собой.

## 4. Примеры промптов и результатов

Промпты — это формулировки, по которым агент выполнял шаги; общие требования (стек, запреты, формат ответа) в них не повторялись, они в `CLAUDE.md`.

**Шаг 2–3. Каркас (шаблон 1, генерация).**
> Роль: старший React-разработчик. Задача: создай клиент для REST API (`/api/tools`, `/api/issues`, `/api/stats`…). Контекст: бэкенд отвечает `{error: "..."}` с кодами 400/404/409; нужно отличать «сервер отказал» от «нет связи». Формат: `src/api/client.js` + `index.js`, один метод на сценарий, тест.

Результат: `request()` с таймаутом 15 с и двумя типами ошибок (`ApiError` с кодом и сообщением сервера, `NetworkError`); тесты на 204, 409, обрыв соединения, 500 без тела.

**Шаг 4. Состояния (шаблон 1).**
> Сделай хук, который выполняет загрузку и отдаёт `loading / error / data / reload`; при неудачной перезагрузке прежние данные не стираются (ТЗ: ERR-NET-01).

Результат: `useAsync` и `useSubmit` (блокирует повторную отправку формы, ERR-NET-05).

**Шаг 5. Тесты (шаблон 3).**
> Напиши тесты страницы «Инструменты»: загрузка и список; пустой результат с кнопкой «Сбросить фильтры»; сетевая ошибка и успешный повтор; форма выдачи: клиентская валидация без запроса и ответ 409 без закрытия формы.

Результат: 4 теста страницы; затем ещё 1 регрессионный (см. ниже).

**Шаг 6. Отладка адаптива (по скриншоту).**
> Окно 480 px: кликаю по строке — ничего не происходит. Локализуй причину и измерь, а не предполагай.

Результат: замер показал, что карточка инструмента на узком экране лежит ниже таблицы (825 px от верха при экране 191–461 px). Причина — не ошибка обработчика, а раскладка.

## 5. Проблемы и их решения

| № | Проблема | Как выяснено | Решение |
|---|---|---|---|
| 1 | **Дефект адаптива:** на узком экране после выбора инструмента карточка не видна (она под всей таблицей) | Скриншот при ширине 480 px и замер положения карточки через консоль | Прокрутка к карточке после выбора, только на экранах уже 1280 px. Проверка в эмуляции 375 px: карточка в зоне видимости (460 из 812 px) |
| 2 | Первое исправление **не сработало** | Прокрутка осталась 0 после клика | Запускал прокрутку сразу при клике, до перерисовки карточки; перенёс в `useEffect` по смене выбранного инструмента |
| 3 | Второе исправление тоже «не работало» в проверке | Ручной вызов `scrollIntoView` мгновенно работал, плавный — нет | Скрытая панель браузера не анимирует плавную прокрутку, значит проверить `smooth` здесь нельзя. Перешёл на мгновенную прокрутку: проверяема и не конфликтует с «уменьшить анимацию». Вывод про `smooth` в реальном браузере — не проверен |
| 4 | После нажатия «Выдать» экран **показал, что ничего не изменилось** | Сверил с API: выдача прошла, статус `issued` | Кадр был снят раньше перерисовки; повторный кадр показал обновление. Ошибки в приложении не было |
| 5 | Тест упал: «найдено несколько элементов с текстом "Выдан"» | Вывод Testing Library показал DOM | Слова есть и в списке фильтра статуса, и в таблице; поиск ограничен таблицей. Ошибка была в тесте |
| 6 | Скрытая панель браузера: `innerHeight = 0`, `requestAnimationFrame` не вызывается | Диагностика через консоль | Убрал `requestAnimationFrame` из кода (карточка есть в DOM всегда, он не нужен) |

Регрессионный тест `scrolls the details panel into view on narrow screens` падает без исправления и проходит с ним (проверено).

## 6. Что оказалось эффективным

- **Измерять, а не смотреть.** Скриншот показал, что что-то не так; координаты из `getBoundingClientRect` показали, что именно и на сколько.
- **Сверка с независимым источником** (ответ API) спасла от ложного «выдача не работает».
- **Единый слой запросов и два типа ошибок** сделали обработку «нет связи» и «сервер отказал» однообразной на всех экранах и легко тестируемой.
- **Подмена `fetch` на таблицу маршрутов** позволила писать тесты без бэкенда и проверять 409 и сетевые сбои.

## 7. Выводы и рекомендации

1. Ошибки раскладки на узких экранах не находятся тестами компонентов; нужны проверка в браузере на фиксированных ширинах и желательно автоматизация (например, Playwright) для разрешений 375 / 768 / 1280 px.
2. Каждому найденному в браузере дефекту нужен регрессионный тест, который сначала красный.
3. Не принимать неудачную проверку за неудачу кода и наоборот: два из шести пунктов проблем (4 и 3) оказались особенностями среды проверки.
4. Для сдачи остаётся: создать репозиторий и выложить (по вашей команде), при необходимости разместить на хостинге, проверить на реальном телефоне.
