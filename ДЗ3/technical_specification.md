Документ предназначен для исполнителя — разработчика или ИИ-инженера (например, Claude Code), который будет доводить существующее приложение `App` до версии 2. Связанные документы: [project_description.md](project_description.md), [user_stories.md](user_stories.md), [ui_concepts/ui_description.md](ui_concepts/ui_description.md). Файл правил для агента — `CLAUDE.md` в корне рабочей папки (его копия — `ДЗ2/rules.md`); ключевые правила стиля продублированы в НФТ-09 и разделе 1.1.

Обозначения: **[есть]** — реализовано в текущем `App`, требуется сохранить поведение; **[v2]** — новое. Требования имеют идентификаторы (ФТ-, НФТ-, ERR-) и ссылки на истории (US-).

## 1. Описание проекта

**Назначение.** Веб-приложение учёта инструментов склада: реестр инструментов, выдача и возврат сотрудникам, контроль сроков, отчёты.

**Цели v2.**
1. Новый интерфейс по концепции 3 «Корпоративный» (боковое меню, таблица, панель деталей).
2. Вход по логину и паролю, роли «Кладовщик» и «Руководитель».
3. Продление срока возврата и отчёт об использовании инструментов.
4. Единая обработка ошибок и состояний «пусто» / «нет связи».

**Не входит (вне объёма).** Интеграции с внешними системами, мобильное приложение, уведомления по почте или SMS, штрихкоды, самостоятельный вход сотрудников-получателей.

### 1.1. Технические условия (обязательны)

| Область | Требование |
|---|---|
| Сервер | Node.js ≥ 22.5, CommonJS, `'use strict'` |
| База данных | SQLite, встроенный `node:sqlite` |
| Клиент | HTML, CSS, JavaScript (ES-модули, `public/js`), без сборщика |
| Зависимости | **Запрещено** добавлять npm-пакеты и CDN-скрипты |

| Тесты | `node:test`, вспомогательная функция `call`, БД `:memory:`; запуск `npm test` |
| SQL | Только параметризованные запросы; многошаговые изменения — внутри `transaction` |
| DOM | Любые данные в `innerHTML` — через `esc()` |
| Схема БД | Изменения (таблица пользователей и др.) — только по отдельному согласованию с заказчиком; в ТЗ они описаны в разделе 6 |

## 3. Функциональные требования

Для каждой функции: что делает, интерфейс, API, правила, критерии приёмки (по ссылке на истории), нефункциональные требования именно к этой функции. Общие НФТ — в разделе 4.

### F1. Каталог инструментов [есть] — US-01, US-02, US-08, US-09

**Описание.** Список инструментов с поиском и фильтрами, карточка, создание, правка, списание, удаление.

**Интерфейс (концепция 3).** Таблица: инв. №, наименование, категория, статус, срок возврата. Над таблицей: поиск, фильтр категории, фильтр статуса, «Добавить инструмент». Клик по строке открывает панель деталей справа (реквизиты, история выдач, действия).

**API**

| Метод и путь | Назначение | Успех | Ошибки |
|---|---|---|---|
| `GET /api/tools?q=&category=&status=` | список | 200 | 400 неизвестный статус или некорректная категория |
| `GET /api/tools/:id` | карточка | 200 | 404 |
| `POST /api/tools` | создать | 201 | 400, 404 (категория), 409 (дубль номера) |
| `PUT /api/tools/:id` | изменить | 200 | 400, 404, 409 |
| `DELETE /api/tools/:id` | удалить | 204 | 404, 409 (есть история выдач) |

**Правила.**
- ФТ-1.1. Поля: `inv_number` (обяз., ≤30, уникален), `name` (обяз., ≤120), `category_id` (обяз.; пустое или нечисловое значение → 400 «Некорректное значение поля «Категория»»; несуществующая категория → 404), `manufacturer` (≤80), `purchase_date` (`ГГГГ-ММ-ДД`), `price` (≥0), `location` (≤120), `note` (≤300).
- ФТ-1.2. Статусы: `in_stock`, `issued`, `repair`, `written_off`; новый инструмент — `in_stock`.
- ФТ-1.3. Статус `issued` меняется только выдачей и возвратом. Ручная установка или снятие → 409.
- ФТ-1.4. Поиск по `name`, `inv_number`, `manufacturer`, подстрока, без учёта регистра **в том числе для кириллицы**. [Есть частично: текущий `LIKE` SQLite регистронезависим только для латиницы, «дрель» не находит «Дрель»; символы `%` и `_` в запросе не экранируются.] Исполнитель обеспечивает регистронезависимый поиск и экранирование без изменения схемы (способ — на его усмотрение, например сравнение в сервисе по приведённым к нижнему регистру значениям); добавить тест на кириллицу.
- ФТ-1.5 [v2]. Списание (смена статуса на `written_off`) и обратный переход из `written_off` доступны только роли «Руководитель»: при попытке кладовщика `PUT /api/tools/:id` с такой сменой — 403 «Недостаточно прав». Списанные исключаются из отчётов и стоимости парка. (В текущем коде обратный переход из «Списан» разрешён всем; решение — в открытом вопросе 6.)
- ФТ-1.6. Инструмент с историей выдач удалять нельзя, только списывать.

**НФТ-F1.** Список из 500 инструментов отображается и фильтруется менее чем за 1 с при серверном поиске; поиск запускается по Enter или через 300 мс после ввода (без «дребезга»); таблица доступна с клавиатуры (строки фокусируются, Enter открывает панель).

### F2. Выдача и возврат [есть] — US-03, US-04

**Описание.** Оформление выдачи инструмента сотруднику и приём возврата.

**API**

| Метод и путь | Тело | Успех | Ошибки |
|---|---|---|---|
| `POST /api/issues` | `{tool_id, employee_id, issued_at?, due_at}` | 201 + запись выдачи | 400, 404 (инструмент / сотрудник), 409 |
| `POST /api/issues/:id/return` | `{returned_at?, condition_note?, to_repair?}` | 200 + запись выдачи | 400, 404, 409 |
| `GET /api/issues?active=1&overdue=1&employee=&tool=` | список | 200 | 400 |

**Правила.**
- ФТ-2.1. Выдать можно только инструмент со статусом `in_stock`. Иначе 409: «Инструмент нельзя выдать: он уже выдан» / «…находится в ремонте» / «…списан».
- ФТ-2.2. `issued_at` по умолчанию — сегодня (локальная дата сервера), допускается указать другую дату; `due_at` обязателен; `due_at` ≥ `issued_at` (сравнение именно с датой выдачи, не с сегодняшним днём) [есть]. Порядок проверок [есть]: сначала валидация полей запроса, затем поиск записей — поэтому запрос возврата несуществующей выдачи с невалидной датой вернёт 400, а не 404.
- ФТ-2.3. Выдача и смена статуса инструмента выполняются одной транзакцией; в БД действует уникальный индекс «одна открытая выдача на инструмент» (защита от гонок).
- ФТ-2.4. Возврат: закрывает выдачу; статус инструмента — `in_stock` или `repair` (если `to_repair`); при ремонте `condition_note` копируется в `note` инструмента.
- ФТ-2.5. Повторный возврат → 409 «Инструмент уже возвращён»; `returned_at` ≥ `issued_at`.
- ФТ-2.6. Форма выдачи: выпадающий список сотрудников с поиском, поле даты (по умолчанию — сегодня + 7 дней [есть]), предупреждение, если срок > 90 дней (не блокирует).

**НФТ-F2.** Выдача оформляется за ≤ 3 действия после выбора инструмента; повторная отправка формы двойным кликом не создаёт дубль (кнопка блокируется на время запроса).

### F3. Контроль просрочек и CSV [есть] — US-05, US-11

- ФТ-3.1. Просрочена выдача без `returned_at`, у которой `due_at` < сегодня; срок «сегодня» не просрочка.
- ФТ-3.2. В таблице и панели деталей: красный текст срока и «−N дн.»; в отчёте — счётчик.
- ФТ-3.3. `GET /api/report/overdue.csv`: `text/csv; charset=utf-8`, BOM, разделитель «;», строки CRLF, заголовок `Content-Disposition: attachment; filename="overdue.csv"`; колонки: Инв. номер, Инструмент, Сотрудник, Подразделение, Выдан, Срок возврата, Дней просрочки.
- ФТ-3.4. Значения, начинающиеся с `=`, `+`, `-`, `@`, табуляции, возврата каретки, экранируются апострофом (защита от CSV-injection); ячейки с `;`, `"`, переводом строки заключаются в кавычки.
- ФТ-3.5. CSV доступен роли «Руководитель» [v2].

**НФТ-F3.** Выгрузка до 1000 строк — менее 2 с; файл открывается в Excel без «кракозябр» (BOM).

### F4. Отчёты [есть частично] — US-07, US-14

- ФТ-4.1 [есть]. `GET /api/stats`: `counts` по статусам, `overdue`, `total_tools` и `total_cost` без списанных, `byCategory`, `topEmployees` (топ-5 по невозвращённым).
- ФТ-4.2 [v2]. `GET /api/report/usage?category=` — по каждому не списанному инструменту: `tool_id`, `inv_number`, `tool_name`, `category`, `issues_count`, `days_in_use` (дни от выдачи до возврата или до сегодня, суммарно), `last_issued_at`; сортировка по `days_in_use` по убыванию, затем по инв. номеру. Категория: некорректный id → 400, несуществующая → 404. Прототип реализован и протестирован в ДЗ2 (`ДЗ2/artifacts/cot_result.patch`).
- ФТ-4.3. Страница «Отчёты»: плитки показателей (концепция 2: «Просрочено» — красная плитка), таблицы по категориям, топ сотрудников, использование инструментов.
- ФТ-4.4. Доступ — только «Руководитель» [v2].

**НФТ-F4.** Отчёт строится менее чем за 2 с на базе до 1000 инструментов и 20 000 выдач (требует проверки замером; индексы `ix_tools_category`, `ix_issues_employee` уже есть).

### F5. Справочники сотрудников и категорий [есть] — US-10, US-12

| Ресурс | Методы | Ограничения |
|---|---|---|
| `/api/employees` (ФТ-5.1) | GET (поиск `q` по ФИО и подразделению), POST, PUT `/:id`, DELETE `/:id` | ФИО обязательно (≤120); должность ≤80; подразделение ≤80; телефон ≤30; удалять нельзя, если есть выдачи (в том числе закрытые) — 409 |
| `/api/categories` (ФТ-5.2) | GET, POST, PUT `/:id`, DELETE `/:id` | название обязательно (≤80), уникально — 409; удалять нельзя, если есть инструменты — 409 |

**НФТ-F5.** Список сотрудников в форме выдачи загружается один раз при открытии страницы и фильтруется на клиенте.

### F6. Вход и роли [v2] — US-06

**Описание.** Аутентификация по логину и паролю; сессия; проверка прав на каждом маршруте.

**API**

| Метод и путь | Назначение | Успех | Ошибки |
|---|---|---|---|
| `POST /api/auth/login` `{login, password}` | вход | 200 `{login, role}`, cookie сессии | 400 (пустые поля), 401, 429 |
| `POST /api/auth/logout` | выход | 204 | — |
| `GET /api/auth/me` | кто я | 200 `{login, role}` | 401 |

**Правила.**
- ФТ-6.1. Пароли хранятся только в виде хеша (`crypto.scrypt` из стандартной библиотеки, уникальная соль на пользователя); пароль в логи и ответы не попадает.
- ФТ-6.2. Сессия — случайный идентификатор (`crypto.randomBytes`), хранится на сервере; cookie `HttpOnly`, `SameSite=Strict` (`Secure` при HTTPS); срок неактивности 8 часов.
- ФТ-6.3. Все маршруты `/api/*`, кроме `/api/auth/login`, требуют сессию (иначе 401); права по матрице раздела 2 (иначе 403).
- ФТ-6.4. После 5 неудачных входов подряд для одного логина — блокировка на 15 минут (429). Сообщение при неверных данных одно и то же для «нет пользователя» и «неверный пароль».
- ФТ-6.5. Статические файлы клиента отдаются без входа, но данных не содержат; клиент при 401 показывает форму входа.
- ФТ-6.6. Начальные пользователи создаются при первом запуске из переменных окружения или скриптом; пароли по умолчанию в код не зашиваются.
- ФТ-6.7. Роль передаётся клиентом только для отображения; решение о доступе принимает сервер.

**НФТ-F6.** Время ответа входа ≤ 500 мс (параметры scrypt подобрать под это); защита от перебора (ФТ-6.4); сообщения об ошибках не раскрывают существование логина.

### F7. Продление срока возврата [v2] — US-13

- ФТ-7.1. `POST /api/issues/:id/extend`, тело `{ "due_at": "ГГГГ-ММ-ДД" }`; успех — 200 и обновлённая запись выдачи. **Внимание:** в `src/app.js` (`handleApi`) любой POST, кроме `/…/return`, сейчас отвечает 201; нужно расширить исключение на `/extend` и на `/api/auth/login` (200), а `POST /api/auth/logout` должен возвращать `undefined` из обработчика, чтобы ответ был 204.
- ФТ-7.2. Ошибки: срок не указан → 400 «Поле «Новый срок возврата» обязательно для заполнения», формат неверный → 400; срок не позже текущего → 400 «Новый срок возврата должен быть позже текущего»; выдача не найдена → 404; уже возвращена → 409 «Инструмент уже возвращён, срок продлить нельзя».
- ФТ-7.3. Изменение выполняется в транзакции; в панели деталей на кнопку «Продлить срок» открывается форма с новой датой.
- ФТ-7.4. История продлений (кто и когда) требует новой таблицы — отдельное согласование; до него продление просто меняет `due_at`.

**НФТ-F7.** Операция идемпотентна для одного и того же значения (повторная отправка той же даты даёт 400 «позже текущего», данные не портятся).

## 7. Обработка ошибок

### 7.1. Принципы

1. Сервер всегда отвечает JSON `{ "error": "<сообщение на русском>" }`; коды: 400 валидация, 401 нет входа, 403 нет прав, 404 не найдено, 409 конфликт состояния, 413 слишком большой запрос, 429 слишком много попыток, 500 внутренняя ошибка (текст «Внутренняя ошибка сервера», подробности только в журнале сервера); добавлен 405 «Метод не поддерживается». Исключение: при превышении размера тела текущий код обрывает соединение (см. ERR-HTTP-03).
2. Клиент показывает причину простым языком и предлагает следующий шаг; технические подробности (трассировка, SQL) пользователю не выводятся.
3. Ошибка в форме не закрывает форму и не стирает введённые данные.
4. Клиентская проверка не заменяет серверную: сервер валидирует всё.

### 7.2. Каталог ошибок и UX-решения

**Ошибки валидации (400)**

| ID | Ситуация | Сообщение | UX-решение |
|---|---|---|---|
| ERR-VAL-01 | Обязательное поле пусто | «Поле «<имя>» обязательно для заполнения» | Сообщение под полем, поле подсвечено рамкой и значком, фокус на первом ошибочном поле; форма не закрывается |
| ERR-VAL-02 | Превышена длина | «Поле «<имя>» длиннее N символов» | Под полем; счётчик символов у длинных полей |
| ERR-VAL-03 | Неверный формат даты | «Поле «<имя>» должно быть датой в формате ГГГГ-ММ-ДД» | Выбор даты через календарь (`input type=date`), ручной ввод не требуется |
| ERR-VAL-04 | Срок возврата раньше выдачи | «Срок возврата не может быть раньше даты выдачи» | Минимальная дата в календаре = дата выдачи; сообщение под полем срока |
| ERR-VAL-05 | Цена отрицательная или нечисловая | «Цена должна быть неотрицательным числом» | Под полем; поле принимает только числа |
| ERR-VAL-06 | Некорректный или пустой идентификатор (например, не выбрана категория) | «Некорректное значение поля «<имя>»» | В форме выбор категории обязателен: сообщение под полем «Категория» |
| ERR-VAL-07 | Некорректный JSON в теле запроса | «Некорректный JSON в теле запроса» | Только при ошибке клиента; общее уведомление, запись в журнал |
| ERR-VAL-08 | Неизвестный статус в фильтре или в данных инструмента | «Неизвестный статус» | Статус выбирается из фиксированного списка, ввод вручную невозможен |

**Не найдено и служебные ошибки HTTP**

| ID | Ситуация | Сообщение | UX-решение |
|---|---|---|---|

## 8. Порядок работы для исполнителя (ИИ-инженера)

1. Прочитать `CLAUDE.md`, этот документ и `src/*.js`. Запустить `npm test` и зафиксировать исходный результат (ожидается 10 из 10).
2. Работать по приоритетам из `user_stories.md`: сначала Must, затем Should, затем Nice. Одна история — один законченный шаг.
3. По каждой новой функции API: маршрут в `buildRoutes()` → метод сервиса или репозитория → тест в `test/api.test.js` (успех + ошибка) → клиент.
4. Изменения схемы БД и добавление зависимостей **не выполнять без отдельного согласования**; если требование этого требует (F6, F7.4), остановиться и задать вопрос.
5. Не ослаблять существующие тесты и не править их жёсткие числа (14 инструментов, одна просрочка): они зависят от порядка. В новых тестах не опираться на жёсткие числа строк, а инструменты для новых выдач брать не из тех, что использует существующий набор (1–7 и 9) — база общая для всех тестов файла.
6. После каждого шага запускать `npm test` и сообщать результат.

## 9. Критерии приёмки релиза

- Все критерии Given-When-Then из `user_stories.md` для историй выбранного релиза выполняются (для Must — все 6 историй).
- `npm test` проходит полностью, добавленные функции покрыты тестами.
- Нет изменений схемы БД и зависимостей, не согласованных отдельно.
- Проверка НФТ-03 и НФТ-04 выполнена вручную на трёх ширинах экрана.
