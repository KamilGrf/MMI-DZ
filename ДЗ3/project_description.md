# АС «Учёт инструментов», версия 2 — описание продукта

Шаг 1 ДЗ3. Продуктовая идея опирается на существующее приложение из ДЗ1–ДЗ2 (папка `App`): Node.js + SQLite + HTML/CSS/JS, без внешних зависимостей. В ДЗ3 оно рассматривается как продукт, для которого проектируется следующая версия: новый интерфейс, вход по ролям и расширенная отчётность.

> **Что уже есть, а что предлагается.** Существующий функционал (справочники, выдача и возврат, просрочки, отчёт, CSV) помечен в тексте как **«есть»**. Новое требование — **«v2»**. Авторизации и ролей в текущей системе нет, это целиком предложение v2.

## 1. Идея

Веб-приложение для небольшого склада инструмента на предприятии (ремонтный цех, монтажный участок, энергослужба): кладовщик фиксирует, какой инструмент у какого сотрудника, до какого срока и в каком состоянии он вернулся; руководитель видит, где инструмент, что просрочено и сколько стоит парк.

## 2. Проблема

| Проблема сегодня | Следствие |
|---|---|
| Учёт ведётся в бумажном журнале или в Excel | Нельзя быстро узнать, у кого инструмент; два человека могут получить один и тот же |
| Нет контроля сроков | Инструмент не возвращается, о просрочке узнают при поиске |
| Нет истории состояния | Непонятно, кто вернул сломанный инструмент, когда он ушёл в ремонт |
| Нет единой картины для руководителя | Инвентаризация и закупки идут «на глаз» |
| Любой, у кого есть доступ к файлу, может его править | Нет ответственности за изменения (проблема v2: нужны вход и роли) |

## 3. Целевая аудитория

| Роль | Кто это | Что хочет | Устройство |
|---|---|---|---|
| **Кладовщик** (основной пользователь) | Сотрудник склада инструмента, 25–55 лет, не обязан быть уверенным пользователем ПК | Быстро выдать и принять инструмент, не ошибиться в сроке и сотруднике | Рабочий ПК на складе, иногда планшет |
| **Руководитель** (заведующий складом, начальник участка) | Принимает решения о закупке и списании | Видеть сводку, просрочки, стоимость парка; выгружать данные | ПК или смартфон, заходит редко и ненадолго |

Сотрудники, получающие инструмент, в систему не входят: они выступают как справочные записи (ФИО, должность, подразделение).

## 4. Ключевые функции MVP

| № | Функция | Статус | Ценность |
|---|---|---|---|
| F1 | Каталог инструментов: поиск, фильтры по категории и статусу, добавление, правка, списание | есть | Единый реестр с инвентарными номерами и статусами (`in_stock`, `issued`, `repair`, `written_off`) |
| F2 | Выдача и возврат инструмента с датой, сроком и состоянием; возврат «в ремонт» | есть | Один инструмент не может быть выдан двум людям; видна история |
| F3 | Контроль просрочек и CSV-выгрузка | есть | Руководитель сразу видит, кто задерживает инструмент |
| F4 | Сводный отчёт: количества по статусам, стоимость, топ сотрудников, использование инструментов | есть (частично), использование — v2 | Основа для решений о закупке и списании |
| F5 | Справочники сотрудников и категорий | есть | Единые данные, защита от удаления используемых записей |
| F6 | Вход в систему и роли «Кладовщик» / «Руководитель» | **v2** | Ответственность за действия, закрытие доступа посторонним |
| F7 | Продление срока возврата | v2 (метод API прототипирован в ДЗ2: `ДЗ2/artifacts/ab_with_rules.patch`) | Не нужно выдавать и принимать заново ради новой даты |

Минимум по заданию — три функции; в документе описано семь. **MVP-релиз = F1–F3 и F6** (истории Must); F4, F5 и F7 — релизы 1.1 и далее (см. карту историй в [user_stories.md](user_stories.md)). Справочники F5 в MVP заполняются начальными данными.

## 5. Ценность

- Время выдачи инструмента — до минуты вместо поиска записи в журнале (целевой показатель v2, замер на пользователях не проводился).
- Ноль «двойных выдач»: ограничение закреплено в схеме БД (уникальный индекс открытой выдачи).
- Просрочки видны без ручной сверки.
- Персональная ответственность за операции после появления входа (F6).

## 6. Ограничения и допущения

- Стек не меняется: Node.js ≥ 22.5, `node:sqlite`, без внешних зависимостей.
- Данные сотрудников в демо-базе вымышленные; для реальной эксплуатации потребуется согласие на обработку персональных данных (вне рамок ДЗ).
- Вход и роли потребуют изменения схемы БД (таблица пользователей), что по правилам проекта согласуется отдельно.
- Интеграция с учётными системами предприятия (1С и т. п.) в MVP не входит.
