# Шаг 1. Анализ проекта и требований

## Выбранный проект

**АС «Учёт инструментов»** — существующее веб-приложение (папка `App`), выбранное и описанное в отчёте ДЗ1. Приложение ведёт учёт инструментов, сотрудников и категорий, оформляет выдачу и возврат, контролирует просроченные возвраты и формирует сводный отчёт (в том числе CSV-выгрузку просрочек). Объём кода — около 1300 строк, 10 автоматических тестов (все проходят: `npm test`).

Задача агента в проекте — развивать готовую систему: добавлять функции, писать тесты, рефакторить, дорабатывать интерфейс.

## Технологический стек

| Часть | Технология |
|---|---|
| Сервер | Node.js ≥ 22.5, CommonJS, встроенный модуль `node:http` |
| База данных | SQLite через встроенный `node:sqlite` (`DatabaseSync`) |
| Клиент | HTML + CSS + JavaScript (ES-модули в `public/js`), без сборщика |
| Тесты | встроенный `node:test` + `node:assert/strict`, БД `:memory:` |
| Зависимости | **отсутствуют** (ни npm-пакетов, ни CDN) |

## Архитектура

Три слоя сервера, зависимости направлены сверху вниз:

```
public/js (api.js → ui.js → views.js)      клиент
src/app.js        HTTP-слой: buildRoutes(), статика, обработка ошибок
src/services.js   бизнес-логика: выдача, возврат, статистика, CSV
src/repositories.js  доступ к данным, класс на таблицу; функции валидации text/date/id; HttpError
src/db.js         SCHEMA и обёртка Database (run/get/all/transaction)
```

## Зафиксированные требования

**Стиль кода** (выведены из существующего кода, а не придуманы):
- `'use strict'` в серверных файлах, отступ 4 пробела, одинарные кавычки, точка с запятой;
- классы — `PascalCase`, функции и переменные — `camelCase`, колонки БД и поля JSON — `snake_case`;
- статусы инструмента — коды `in_stock`, `issued`, `repair`, `written_off`;
- комментарии на русском и только «зачем» (привязка к use case);
- сообщения пользователю — на русском, формат «Поле «...» ...», даты `ГГГГ-ММ-ДД`.

**Архитектура и стандарты:**
- ошибки — только через `HttpError(status, message)`: 400 валидация, 404 не найдено, 409 конфликт состояния;
- входные данные валидируются функциями `text`, `date`, `id`;
- многошаговые изменения БД — внутри `database.transaction`;
- новая функция API проходит все слои: маршрут → сервис/репозиторий → тест (успех + минимум одна ошибка).

**Ограничения безопасности и целостности:** только параметризованный SQL; `esc()` для всего, что идёт в `innerHTML`; без внешних зависимостей; схема БД и `data/tools.db` не меняются без отдельного указания; тесты нельзя ослаблять.

Эти требования закреплены в [rules.md](rules.md).
