# Шаг 4. Chain-of-Thought: цепочка промптов

## Выбранная задача

**«Отчёт об использовании инструментов»** — для каждого не списанного инструмента показать число выдач, суммарное число дней «на руках» и дату последней выдачи; с фильтром по категории; вывести таблицей на странице «Отчёт».

Почему задача сложная: затрагивает все слои (SQL → сервис → маршрут → тест → клиент), нужно посчитать дни и для невозвращённых выдач (до сегодняшнего дня), а схему БД менять нельзя.

Приём Chain-of-Thought здесь — не один большой запрос «сделай отчёт», а цепочка из 5 шагов: каждый следующий промпт опирается на проверенный результат предыдущего, а в каждом шаге агент сначала рассуждает (план/допущения), потом действует.

Выполнялось агентом Claude Code с включённым файлом правил [rules.md](rules.md) на копии приложения (оригинал `App` не изменён). Итоговый код — [artifacts/cot_result.patch](artifacts/cot_result.patch).

---

## Шаг 1. Декомпозиция (шаблон 5)

**Промпт**
```
[Role] Ты — архитектор-аналитик: разбиваешь крупные задачи на небольшие проверяемые шаги.
[Task] Раздели задачу «Отчёт об использовании инструментов» на подзадачи. Код пока не пиши.
[Context] Для каждого не списанного инструмента: число выдач, дни на руках, дата последней выдачи.
Фильтр по категории. Таблица на странице «Отчёт». Схему БД не менять.
[Format] Таблица: № | Подзадача | Файлы | Как проверить. В конце — допущения и риски.
```

**Результат (план, по которому шла работа)**

| № | Подзадача | Файлы | Как проверить |
|---|---|---|---|
| 2 | SQL-запрос и метод сервиса `usageReport` | `src/services.js` | вызов через API на демо-данных |
| 3 | Маршрут `GET /api/report/usage` | `src/app.js` | ответ 200, `?category=abc` → 400 |
| 4 | Тест: успех + 400 + 404 | `test/api.test.js` | `npm test` |
| 5 | Таблица на странице «Отчёт» | `public/js/views.js` | значения подставляются через `esc()` |

Допущения, зафиксированные на этом шаге:
- дни «на руках» = разница дат возврата (или сегодняшней даты для невозвращённой выдачи) и даты выдачи, суммируются по всем выдачам инструмента;
- инструмент без выдач тоже попадает в отчёт (0 выдач, дата `null`);
- списанные инструменты в отчёт не входят;
- несуществующая категория в фильтре — 404, а не пустой список (как в других методах проекта через `CategoryRepository.get`).

## Шаг 2. SQL и сервис

**Промпт**
```
[Role] Старший Node.js-разработчик.
[Task] Реализуй IssueService.usageReport({ category }) в src/services.js по плану шага 1.
[Context] Образец стиля: IssueService.stats(). Только параметризованный SQL. Валидация категории —
функция id() и CategoryRepository.get. Схему БД не менять.
[Format] Точечный дифф services.js, без переписывания файла. Комментарий — на русском, с привязкой к use case.
```

**Результат** — метод в `src/services.js`: один запрос `tools JOIN categories LEFT JOIN issues` с группировкой по инструменту; дни считаются как `julianday(COALESCE(returned_at, сегодня)) − julianday(issued_at)`; фильтр по категории добавляется через `?`-параметр. Заодно в импорт добавлен `CategoryRepository`. Сортировка: по дням на руках по убыванию, затем по инвентарному номеру.

**Промпт**
```

Сделай одну строку, остальное в app.js не трогай.
```

**Результат** — одна добавленная строка в `buildRoutes()`. Проверка на запущенном сервере: `GET /api/report/usage?category=1` вернул JSON с полями `tool_id, inv_number, tool_name, category, issues_count, days_in_use, last_issued_at` (для дрели `ИНВ-0001`: 1 выдача, 10 дней); `?category=abc` → HTTP 400.

## Шаг 4. Тесты (шаблон 3)

**Промпт**
```
[Role] Инженер по тестированию на node:test.
[Task] Добавь в конец test/api.test.js тест для GET /api/report/usage.
[Context] Сценарии: все строки, дни для невозвращённой выдачи (инструмент 1 выдан 10 дней назад),
инструмент без выдач, фильтр по категории, ?category=abc → 400, ?category=999 → 404.
Существующие тесты не менять.
[Format] Код теста + результат npm test.
```

**Результат — с ошибкой на первой попытке.** Первый вариант теста проверял `all.data.length === 14`. `npm test`: 10 прошли, 1 упал (`13 !== 14`).

Разбор: первопричина — не в коде отчёта, а в допущении теста. Соседний тест «статус «Выдан» нельзя поставить вручную; списание» списывает инструмент 9, а списанные в отчёт не входят, поэтому корректный результат — 13. Этот риск (общее состояние БД между тестами) при декомпозиции учтён не был; он выявился только по падению теста и после этого добавлен в контекст шаблона 3. Исправление: ожидаемое число строк берётся из `GET /api/stats` (`total_tools`), которое тоже считает только не списанные инструменты. Проверка не ослаблена, ожидание привязано к независимому источнику.

После исправления: `npm test` — 11 тестов, 11 прошли, 0 упали.

## Итог

| Показатель | Значение |
|---|---|
| Шагов в цепочке | 5 (декомпозиция + 4 исполнительных) |
| Изменённые файлы | `src/services.js`, `src/app.js`, `test/api.test.js`, `public/js/views.js` |
| Результат `npm test` | 11 из 11 (было 10; добавлен 1 тест) |
| Схема БД, `package.json` | не менялись |

**Что проверено, а что нет.** Серверная часть проверена автоматическим тестом и живым запросом к запущенному серверу. Клиентская таблица (шаг 5) в браузере не открывалась — проверен только код; визуальную проверку нужно сделать вручную на странице «Отчёт» (`npm start`, http://localhost:3000/#stats).

**Что дала цепочка.** Разделение на шаги позволило поймать ошибку локально: когда упал тест, было ясно, что отчёт и маршрут уже проверены вручную на шаге 3, значит проблема в самом тесте. Допущения (списанные, 404 для категории) были зафиксированы до написания кода, а не выяснялись по ходу.
