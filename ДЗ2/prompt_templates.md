# Шаг 3. Библиотека промпт-шаблонов (RTCF)

Все шаблоны построены по структуре **RTCF**: Role (роль) · Task (задача) · Context (контекст) · Format (формат). Места для подстановки отмечены `{{...}}`. Шаблоны рассчитаны на проект «Учёт инструментов» и работают вместе с файлом правил [rules.md](rules.md): общие требования (стек, стиль, запреты) в каждый промпт повторять не нужно, в шаблонах оставлено только то, что специфично для сценария.

| № | Сценарий | Когда применять |
|---|---|---|
| 1 | Генерация функции / метода API | нужна новая возможность |
| 2 | Рефакторинг | код работает, но плохо читается или дублируется |
| 3 | Написание тестов | есть код без покрытия |
| 4 | Исправление бага | есть воспроизводимая ошибка |
| 5 | Декомпозиция задачи | задача слишком большая для одного промпта |

---

## Шаблон 1. Генерация функции или метода API

**Role**
```
Ты — старший full-stack разработчик на Node.js, который развивает существующую систему
и не ломает сложившуюся архитектуру.
```

**Task**
```
Реализуй {{что нужно: метод API / функцию / компонент}}: {{описание поведения}}.
Определи, в каких слоях нужны изменения, и сделай их.
```

**Context**
```
- Use case: {{название сценария}}.
- Входные данные: {{поля, формат}}.
- Правила и ошибки: {{условие → код ответа и текст}}.
- Образец для подражания: {{файл и функция, например IssueService.returnTool в src/services.js}}.
- Что нельзя менять: {{схема БД, существующие тесты и т. п.}}.
```

**Format**
```
1. Кратко (3–5 строк): план изменений по слоям.
2. Изменения точечно, по файлам, с путями. Файлы целиком не переписывать.
3. Тест(ы): успешный сценарий и минимум одна ошибка.
4. Результат `npm test`.
5. Если приняты допущения — отдельным списком в конце.
```

**Пример использования**
```
[Role] Ты — старший full-stack разработчик на Node.js ...
[Task] Реализуй метод API «продлить срок возврата»: меняет due_at у невозвращённой выдачи.
[Context]
- Use case: «Продлить срок возврата».
- Вход: POST /api/issues/:id/extend, тело { "due_at": "ГГГГ-ММ-ДД" }.
- Ошибки: нет due_at или формат неверный → 400; новый срок не позже текущего → 400;
  выдача не найдена → 404; инструмент уже возвращён → 409.
- Образец: IssueService.returnTool в src/services.js.
- Схему БД не менять.
[Format] как в шаблоне.
```
Реальный результат подобной задачи (с короткой формулировкой, без полного шаблона) — в [testing.md](testing.md).

## Шаблон 2. Рефакторинг с улучшением

**Role**
```
Ты — старший разработчик, специализирующийся на безопасном рефакторинге:
поведение системы после твоих изменений остаётся прежним.
```

**Task**
```
Отрефактори {{функцию/класс/файл}}: {{цель — убрать дублирование / упростить / разделить ответственность}}.
Внешнее поведение (ответы API, тексты ошибок, статусы) менять нельзя.
```

**Context**
```
- Файл и участок: {{путь:строки}}.
- Проблема: {{что именно плохо}}.
- Страховка: тесты в test/api.test.js должны проходить без изменений.
- Ограничения: {{не трогать публичные сигнатуры, не добавлять зависимости}}.
```

**Format**
```
1. Что не так (список проблем с указанием строк).
2. Что меняешь и почему (по пунктам).
3. Изменения точечным диффом.
4. Подтверждение, что поведение не изменилось: результат `npm test` до и после.
```

**Пример использования**
```
[Task] Отрефактори public/js/views.js, класс StatsView.render: убрать повторяющийся код
построения таблиц, вынеся его во вспомогательную функцию table(headers, rows).
[Context]
- public/js/views.js, StatsView.render: несколько почти одинаковых таблиц собираются вручную строками.
- Все значения по-прежнему должны экранироваться через esc().
- Серверные тесты менять нельзя; внешний вид страницы «Отчёт» должен остаться тем же.
[Format] как в шаблоне; npm test до/после.
```

## Шаблон 3. Написание тестов

**Role**
```
Ты — инженер по тестированию (QA automation) на Node.js, пишешь тесты на встроенном node:test.
```

**Task**
```
Напиши тесты для {{метода/эндпоинта}}. Покрой успешный сценарий, граничные значения
и все ветки ошибок.
```

**Context**
```
- Тестируемый код: {{путь и имя}}.
- Поведение: {{коротко, или «изучи код сам»}}.
- Окружение тестов: test/api.test.js, вспомогательная функция call(method, url, body), БД :memory:
  с демо-данными (14 инструментов; состояние общее для всех тестов файла, порядок тестов важен).
- Существующие тесты не менять и не ослаблять.
```

**Format**
```
1. Таблица тест-кейсов: «Ситуация | Ожидаемый ответ».
2. Код тестов, добавляемый в конец test/api.test.js, названия — на русском.
3. Результат `npm test`; если тест упал — разобрать, ошибка в коде или в тесте, и не подгонять ожидание.
```

**Пример использования**
```
[Task] Напиши тесты для GET /api/report/usage (отчёт об использовании инструментов).
[Context]
- src/services.js, IssueService.usageReport.
- Поведение: по каждому не списанному инструменту — число выдач, дни «на руках», дата последней выдачи;
  фильтр ?category=<id>; ошибки: category=abc → 400, category=999 → 404.
- Состояние БД общее: другие тесты списывают инструмент 9 — не хардкодить число строк.
[Format] как в шаблоне.
```
Это тот случай из [prompt_methodology.md](prompt_methodology.md), где тест сначала упал из-за жёстко заданного числа строк (14): состояние общей БД уже изменил соседний тест. Строка про «не хардкодить» в контексте шаблона — вывод из этой ошибки.

## Шаблон 4. Исправление бага

**Role**
```
Ты — опытный разработчик-отладчик: сначала находишь первопричину, потом чинишь,
и обязательно добавляешь тест, который воспроизводит ошибку.
```

**Task**
```
Найди и исправь ошибку: {{симптом}}.
Не чини симптом в обход причины и не меняй несвязанный код.
```

**Context**
```
- Ожидаемое поведение: {{...}}.
- Фактическое поведение: {{...}}.
- Шаги воспроизведения / запрос: {{метод, URL, тело}}.
- Сообщение об ошибке / лог: {{текст}}.
- Подозрительные файлы (если известны): {{...}}.
```

**Format**
```
1. Первопричина (1–3 предложения, со ссылкой на файл:строку).
2. Тест, который падает до исправления (покажи падение).
3. Минимальное исправление диффом.
4. Результат `npm test` — все тесты зелёные.
5. Могут ли аналогичные места в других функциях иметь ту же ошибку (проверь поиском).
```

**Пример использования**
```
[Task] Найди и исправь ошибку: при возврате инструмента «в ремонт» его примечание (note) не обновляется
из поля condition_note.
[Context]
- Ожидаемо: tools.note = condition_note, если to_repair = true.
- Фактически: note остаётся прежним (проверка: GET /api/tools/7 после POST /api/issues/:id/return
  с { "condition_note": "Треснула рукоятка", "to_repair": true }).
- Подозрение: IssueService.returnTool, запрос UPDATE tools ... COALESCE(?, note).
[Format] как в шаблоне.
```
Пример учебный: в текущей версии код ведёт себя правильно, так что на практике агент должен ответить, что воспроизвести ошибку не удалось, и показать проверку. Шаблон демонстрирует формулировку запроса, а не найденный дефект.

## Шаблон 5. Декомпозиция сложной задачи

**Role**
```
Ты — архитектор-аналитик: разбиваешь крупные задачи на небольшие проверяемые шаги,
которые можно выполнить и проверить по отдельности.
```

**Task**
```
Раздели задачу «{{формулировка}}» на последовательные подзадачи. Код пока не пиши.
```

**Context**
```
- Цель и пользовательская ценность: {{...}}.
- Затрагиваемые слои: {{БД / сервис / API / клиент / тесты}}.
- Ограничения: {{из rules.md и специфичные, например «схему не менять»}}.
- Критерий готовности всей задачи: {{...}}.
```

**Format**
```
Таблица: № | Подзадача | Файлы | Зависит от | Как проверить.
Каждая подзадача — не более одного слоя и не более ~50 строк кода.
В конце: порядок выполнения, риски и вопросы, без ответа на которые нельзя начинать.
```

**Пример использования**
```
[Task] Раздели задачу «Отчёт об использовании инструментов»: для каждого инструмента показать число выдач,
сколько дней он был на руках и дату последней выдачи, с фильтром по категории и таблицей на странице «Отчёт».
[Context]
- Слои: SQL-запрос, сервис, маршрут API, клиент (StatsView), тесты.
- Ограничения: схему БД не менять; списанные инструменты в отчёт не входят.
- Готовность: npm test зелёный, таблица видна на странице «Отчёт».
[Format] как в шаблоне.
```
Этот запрос — первый шаг цепочки в [prompt_methodology.md](prompt_methodology.md).
