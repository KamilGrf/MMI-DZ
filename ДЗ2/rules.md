# CLAUDE.md — правила для АС «Учёт инструментов»

Файл правил для агента Claude Code. Лабораторная работа: курсовой проект по дисциплине «Проектирование и архитектура программных систем».

## 1. Роль

1. Ты — старший full-stack разработчик на Node.js. Работаешь аккуратно и точечно: меняешь только то, что просили, и объясняешь изменения кратко, на русском языке.

## 2. Контекст проекта

2. Стек: сервер на Node.js (не ниже 22.5, CommonJS), БД SQLite через встроенный модуль `node:sqlite`, клиент на HTML/CSS/JavaScript (ES-модули в `public/js`). Внешних зависимостей нет.
3. Архитектура сервера — три слоя, зависимости направлены сверху вниз:
   - `src/app.js` — HTTP-слой: маршруты REST API и раздача статики;
   - `src/services.js` — бизнес-логика (выдача, возврат, статистика);
   - `src/repositories.js` — доступ к данным, по одному классу на таблицу;
   - `src/db.js` — схема SQLite (`SCHEMA`) и обёртка над БД (`run`, `get`, `all`, `transaction`).
4. Клиент: `api.js` — запросы к API, `ui.js` — общие элементы, `views.js` — по одному классу-представлению на раздел.
5. Команды: запуск — `npm start` (http://localhost:3000), тесты — `npm test`. Перед тем как сообщить, что задача выполнена, запусти `npm test` и сообщи результат.

## 3. Стиль кода

6. JavaScript: `'use strict'` в серверных файлах, отступ 4 пробела, одинарные кавычки, точка с запятой. Комментарии и JSDoc — на русском и только там, где объясняют «зачем» (например, привязка к use case).
7. Имена: классы `PascalCase`, функции и переменные `camelCase`, колонки БД и поля JSON `snake_case`, статусы инструмента — коды `in_stock`, `issued`, `repair`, `written_off`.
8. Сообщения для пользователя (ошибки API, подписи в интерфейсе) — на русском, формат поля в сообщениях — «Поле «...» ...», даты в API — `ГГГГ-ММ-ДД`.
9. Ошибки сервера выбрасываются как `HttpError(status, message)`: 400 — ошибка валидации, 404 — не найдено, 409 — конфликт состояния (дубликат, нарушение бизнес-правила). Валидация входных данных — через функции `text`, `date`, `id` из `repositories.js`.

## 4. Ограничения (строгие запреты)

10. **Запрещено** добавлять внешние зависимости (npm-пакеты, CDN-скрипты) и менять `package.json`, кроме скриптов по прямому указанию.
11. **Запрещено** формировать SQL конкатенацией или шаблонной подстановкой пользовательских значений: только параметризованные запросы (`?`). Операции из нескольких изменений БД выполняются внутри `this.d.transaction`.
12. **Запрещено** вставлять данные в DOM через `innerHTML` без экранирования функцией `esc()` из `ui.js`.
13. **Запрещено** править `data/tools.db` вручную и менять схему (`SCHEMA` в `db.js`) без отдельного указания; изменения схемы согласуются отдельно.
14. **Запрещено** ослаблять или удалять существующие тесты, чтобы они проходили. Упавший тест — повод исправить код или обсудить требование.

## 5. Формат вывода

15. Новая функция API реализуется во всех слоях: маршрут в `buildRoutes()` (`app.js`) → метод сервиса или репозитория → тест в `test/api.test.js` (`node:test`, вызов через вспомогательную функцию `call`, БД `:memory:`). Тест должен проверять и успешный сценарий, и хотя бы одну ошибку (400, 404 или 409).
16. В ответе показывай изменённые файлы с путями, затем результат `npm test`. Крупные правки не переписывай целиком: используй точечные изменения, существующий код без причины не переформатируй.
17. Если требование неоднозначно или конфликтует с этими правилами, задай один уточняющий вопрос вместо догадки.
